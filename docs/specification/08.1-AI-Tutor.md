# Chapter 8 — AI Tutor Foundation

## Vision

The AI Tutor is a contextual Japanese language assistant embedded inside Kotoba Compass.

It is NOT a general-purpose chatbot.

The AI Tutor exists solely to help users comprehend, deconstruct, and learn from the currently selected Japanese text during immersion reading.

---

## Core Design Philosophy

Kotoba Compass follows the immersion learning cycle:

```
Reading ──► Understanding ──► Learning ──► Back to Reading
```

The AI Tutor supports this cycle without distracting the learner.

Unlike general assistants (ChatGPT, Gemini, Claude), the AI Tutor is strictly bound to the currently selected text. It does not maintain open-ended chat threads or answer non-Japanese questions.

---

## Information Priority Hierarchy

When explaining Japanese text, information sources follow an absolute precedence hierarchy:

```
1. Language Analysis Engine output (Highest Priority)
2. Dictionary data
3. Grammar analysis
4. AI reasoning (Lowest Priority)
```

The AI Tutor exists to explain and contextualize pre-analyzed language data. It is NOT a secondary analysis engine. Whenever supplied analysis context conflicts with an AI model's internal reasoning, the supplied analysis context MUST take absolute precedence.

---

## Mandatory Response Constraints

All current and future AI providers (Mock, Gemini, OpenAI, Claude, OpenRouter, Local LLMs) MUST strictly enforce the following rules:

- **Explain only the currently selected Japanese text.**
- **Never answer unrelated questions.**
- **Never become a general-purpose chatbot.**
- **Prefer supplied analysis over inference.**
- **Never contradict supplied dictionary results.**
- **Never contradict supplied grammar analysis.**
- **Never introduce new grammar concepts unless directly required to explain the selected text.**
- **Keep responses concise.**
- **Admit uncertainty whenever appropriate.**
- **Request more context instead of hallucinating.**
- **Never fabricate grammar rules, meanings, or conjugations.**

---

## Architecture & Layer Isolation

The AI Tutor subsystem enforces strict layer isolation across decoupled components:

```
[UI Component (TutorView)]
         │
         ▼
[AiTutorService] (Single Orchestration Layer)
    ├──► [QuestionValidator] (Relevance verification)
    ├──► [PromptBuilder]     (Generates provider-agnostic PromptMessages)
    └──► [AiTutorProvider]   (Consumes ONLY PromptMessages ──► Output AiTutorResponse)
```

### Mandatory Dependency Constraints
- **`TutorView`**: Communicates EXCLUSIVELY with `AiTutorService`. Has zero direct knowledge of providers, prompts, or `AiTutorRequest`.
- **`AiTutorService`**: Single orchestration layer. Constructs internal `AiTutorRequest`, handles prompt generation, validation, timeout, cancellation (`AbortController`), error normalization, and provider dispatch.
- **`QuestionValidator`**: Evaluates prompt relevance. Unaware of AI providers or UI layouts.
- **`PromptBuilder`**: Constructs provider-agnostic `PromptMessages` (`system`, `context`, `user`). Unaware of provider-specific API payloads or schemas.
- **`AiTutorProvider`**: Consumes **ONLY** `PromptMessages`. Does NOT receive `AiTutorRequest`, UI models, or raw context objects. Converts `PromptMessages` to provider-specific payloads and returns `AiTutorResponse`. Unaware of UI or prompt building logic.

---

## Provider Capabilities Model

Each `AiTutorProvider` exposes a capability contract to prevent provider-specific conditionals throughout the codebase:

```ts
export interface ProviderCapabilities {
  supportsStreaming: boolean;
  supportsExamples: boolean;
  supportsImages: boolean;
  supportsAudio: boolean;
}

export interface AiTutorProvider {
  readonly name: string;
  readonly capabilities: ProviderCapabilities;
  isConfigured(): boolean;
  explain(messages: PromptMessages): Promise<AiTutorResponse>;
}
```

---

## Structured Data Models & Schema Stability

### 1. Intermediate Prompt Representation
`PromptBuilder` output consumed by providers:
```ts
export interface PromptMessages {
  system: string;
  context: string;
  user: string;
}
```

### 2. Stable Response Schema (`AiTutorResponse`)
`AiTutorResponse` is a stable architectural contract. Future providers may extend it with optional metadata, but core field semantics (`summary`, `grammar`, `nuance`, `example`, `commonMistake`) must remain identical regardless of provider:

```ts
export interface AiTutorExample {
  japanese: string;
  english: string;
  explanation?: string;
}

export interface AiTutorResponse {
  summary: string;
  grammar?: string;
  nuance?: string;
  example?: AiTutorExample;
  commonMistake?: string;
  learningTip?: string;
  needsMoreContext?: boolean;
  providerName: string;
  model?: string;
  cached?: boolean;
  responseTimeMs?: number;
}
```

### 3. Action Model for Suggested Questions
```ts
export enum TutorAction {
  Explain = 'explain',
  Grammar = 'grammar',
  Nuance = 'nuance',
  Example = 'example',
  Mistakes = 'mistakes',
}
```

---

## "Not Enough Context" Handling

When a user selects an isolated character or particle with insufficient context (e.g., は, を, だけ), providers MUST NOT hallucinate grammar explanations. Instead, the service returns a response with `needsMoreContext: true` requesting surrounding context.

---

## Mock Provider Specification

`MockAiTutorProvider` returns deterministic, canned, repeatable outputs. It returns `false` for all optional `capabilities`. Its sole purpose is testing, architecture verification, and offline development.
